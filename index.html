Worum geht es?

Wir programmieren die Export-Funktion einer Notenverwaltung. Lehrkräfte können ihre Notenliste und die Fehlzeitenliste als CSV (zum Öffnen in Excel) oder als PDF (zum Ausdrucken) exportieren. Schauen wir uns zuerst an, wie man das ohne Entwurfsmuster lösen würde und wo es hakt.

Die „naive“ Lösung

Die Klasse ExportDienst kann zwei Listen exportieren: die Noten und die Fehlzeiten. In beiden Methoden entscheidet sie mit if-Abfragen selbst, welches Objekt sie mit new erzeugt.

👉 Die Schul-App soll die Noten künftig auch als JSON einlesen können. Klicke auf den Button und beobachte, was im bestehenden Code passieren muss.

0Zeilen in bestehendem, getestetem Code eingefügt
3konkrete Klassen, von denen ExportDienst jetzt abhängt

Die Probleme:

  • Starke Kopplung: ExportDienst kennt jede einzelne Dokument-Klasse beim Namen.
  • Jede Erweiterung ist ein Eingriff: Für jedes neue Format müssen wir alte Methoden öffnen und ändern, und zwar an mehreren Stellen.
  • Doppelter Code: Die gleiche Erzeugungslogik steht zweimal da. Vergisst man eine Stelle, gibt es JSON nur für die Noten, aber nicht für die Fehlzeiten. Das fällt erst zur Laufzeit auf.
  • Keine gemeinsame Schnittstelle: SchreibeCsv(), ErzeugePdf(), ToJson(): Jede Dokument-Klasse wird anders bedient.

Erster Schritt: Die Simple Factory

Die einfachste Verbesserung: Wir geben allen Formaten ein gemeinsames Interface IDokument und schieben das ganze new-Geschäft in eine eigene Klasse, die Fabrik. Beide Export-Methoden bestellen dort nur noch: „Gib mir ein Dokument im Format X.“

Bilanz der Simple Factory

  • Gemeinsames Interface: Alle Formate werden gleich bedient: Formatiere().
  • Erzeugung an einer Stelle: Alle new-Aufrufe stehen in der Fabrik.
  • Lose Kopplung: ExportDienst kennt keine konkrete Dokument-Klasse mehr.
  • Nicht geschlossen für Änderung: Jedes neue Format heißt, die Fabrik zu ändern.
  • Der switch wächst und wird mit jedem Format unübersichtlicher.
  • Tippfehler wie "cvs" fallen erst zur Laufzeit auf (Exception).

ℹ️ Die Simple Factory ist ein verbreitetes Programmier-Idiom, aber kein Muster aus dem GoF-Buch.

💡 Die Idee für den nächsten Schritt

Was wäre, wenn es gar keinen switch mehr gäbe? Stattdessen bekommt jedes Format seine eigene Unterklasse des Exporters, und jede Unterklasse weiß selbst, welches Dokument sie braucht. Ein neues Format bedeutet dann nur noch: neue Klassen schreiben, nichts Bestehendes ändern. Genau das ist die Factory Method.

Die vier Rollen des Musters

Die Simple Factory hatte noch einen switch, der bei jedem neuen Format geändert werden muss. Die Factory Method ersetzt diesen switch durch Vererbung: Jedes Format bekommt seinen eigenen Exporter. Es entstehen zwei parallele Klassen-Hierarchien: links die Erzeuger, rechts die Produkte. Klicke auf eine Klasse, um ihre Aufgabe und ihren Code zu sehen.

Erzeuger-Seite (Creator) Produkt-Seite (Product) ── ▷ erbt / implementiert - - → erzeugt / benutzt kursiv = abstrakt

    Merkblatt: Factory Method

    Absicht des Musters (sinngemäß nach Gamma et al., „Design Patterns“, 1994)
    Definiere eine Schnittstelle zum Erzeugen eines Objekts, aber lass Unterklassen entscheiden, welche Klasse instanziiert wird.

    Rezept in 4 Schritten

    1. Gemeinsames Produkt-Interface festlegen (IDokument).
    2. Im Creator eine (meist abstrakte) Methode deklarieren, die dieses Interface zurückgibt (ErstelleDokument()).
    3. Die Logik im Creator (Exportiere()) ruft nur diese Methode auf, nie new mit einer konkreten Klasse.
    4. Für jedes Produkt einen ConcreteCreator schreiben, der die Factory Method überschreibt (CsvExporter, PdfExporter, …).

    Vor- und Nachteile

    • Lose Kopplung: Der Creator kennt keine konkreten Produkte.
    • Offen für Erweiterung, geschlossen für Änderung (Open/Closed-Prinzip).
    • Eine Verantwortung: Die Objekterzeugung steht an genau einer Stelle.
    • Mehr Klassen: Für jedes Produkt oft ein eigener Creator.
    • Für sehr kleine Programme kann das Muster überdimensioniert sein.

    „Aber irgendwo muss doch new stehen?“

    Richtig! Das Muster schafft die Entscheidung welches Objekt nicht ab. Es verschiebt sie an den Rand des Programms, an eine einzige Stelle (bei uns: den Menüaufbau). Die Logik, was mit dem Objekt passiert, wird davon getrennt und muss nie wieder geändert werden.

    Ursprünglich dachten die GoF-Autoren vor allem an Frameworks und Bibliotheken: Gehört Exporter zu einer fremden Bibliothek, kann man deren Code gar nicht ändern, aber man kann eine Unterklasse schreiben. Die Factory Method ist der eingebaute „Haken“, an dem man sein eigenes Produkt einhängt. → Das probierst du auf der Bonus-Seite aus.

    Typische Verwechslungen

    • „Simple Factory“ (eine Klasse mit einer if/switch-Methode, die Objekte erzeugt) ist kein GoF-Muster. Die Factory Method arbeitet mit Vererbung und Überschreiben statt mit Fallunterscheidungen.
    • Abstract Factory erzeugt ganze Familien zusammengehöriger Objekte. Die Factory Method erzeugt ein Produkt.
    • Die Factory Method muss nicht abstrakt sein: Der Creator darf auch ein Standardprodukt zurückgeben (z. B. CSV), das Unterklassen bei Bedarf ändern. In C# ist sie dann virtual statt abstract.
    Weiter: Bonus – Erweitern einer Bibliothek →

    Bonus: Erweitern, ohne den Code ändern zu können

    Eure Schule nutzt die fertige Bibliothek SchulExport (z. B. über NuGet installiert). Sie kann CSV und PDF und erledigt nebenbei viel Arbeit: Kopfzeile, Speichern, Fehlerbehandlung, Protokoll. Jetzt kommt eine neue Zeugnissoftware, und die braucht XML. Das Problem: Die Bibliothek gibt es nur als fertige DLL. Ihren Code könnt ihr nicht ändern.

    🔒 Warum nicht einfach die Bibliothek ändern?

    • Ihr habt nur die kompilierte DLL, nicht den Quellcode.
    • Selbst wenn ihr ihn hättet: Beim nächsten Update der Bibliothek wäre eure Änderung wieder weg.
    • Andere Schulen nutzen dieselbe Bibliothek. Die Entwickler werden sie nicht für eine einzelne Schule umbauen.

    ❌ Hätte die Bibliothek eine Simple Factory …

    … müsstet ihr den switch in der DLL um case "xml" erweitern. Das ist unmöglich, und ihr säßet fest.

    ✅ Die Bibliothek nutzt eine Factory Method: So klappt es

    Ihr schreibt zwei Klassen in eurem eigenen Projekt. Spiele durch, wer wann wen aufruft. Achte auf die Sprünge zwischen Bibliothek und eurem Code.

    💡 Das Hollywood-Prinzip

    „Don’t call us, we’ll call you.“ Nicht euer Code ruft die Bibliothek Schritt für Schritt auf. Die Bibliothek ruft euren Code auf, genau an der Stelle, die sie dafür vorgesehen hat: der Factory Method.

    Genau dafür haben die GoF-Autoren das Muster beschrieben: Ein Framework legt den Ablauf fest, und die Nutzer des Frameworks bestimmen über Unterklassen, welche Objekte darin verwendet werden, ohne eine einzige Zeile des Frameworks zu ändern.
